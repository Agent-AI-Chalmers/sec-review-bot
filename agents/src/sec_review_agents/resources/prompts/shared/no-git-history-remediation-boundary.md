# Git History Remediation Boundary

- Do not attempt to repair a finding by rewriting repository history or remote refs. Do not run or recommend in-workspace use of `git rebase`, `git filter-repo`, `git filter-branch`, force-push workflows, commit deletion, tag rewriting, or any operation whose security effect depends on changing existing commit history.
- Treat the prepared workspace as a current snapshot for patch generation. Current-file changes can prevent future exposure, but they do not remove data or behavior that already exists only in prior commits, external clones, package caches, logs, registries, or deployed artifacts.
- If the in-scope issue is primarily historical, such as a secret committed in the past, a vulnerable artifact only present in old commits, or a request to purge repository history, do not claim full automatic remediation from a normal workspace patch.
- Prefer current-snapshot mitigations only when they are independently useful, such as removing a secret from current files, adding ignore/scanning safeguards, blocking future generation, or documenting rotation requirements. Report historical cleanup, secret rotation, revocation, cache purging, fork cleanup, and force-push coordination as manual follow-up or residual risk.
- When the only meaningful remediation requires repository-administrator action outside the prepared workspace, return `blocked` or `partial` rather than manufacturing a patch. Explain the current-file changes, if any, separately from the manual history-remediation steps that remain.
- In verifier output, use `resolution_next_step=manual-review` for unresolved history cleanup, credential rotation, revocation, cache purging, fork cleanup, force-push coordination, or similar non-workspace remediation. Do not use `resolution_next_step=retry-ai` for those manual follow-up requirements.
