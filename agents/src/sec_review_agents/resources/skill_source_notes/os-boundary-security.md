# OS Boundary Security Source Notes

Reviewed 2026-10-16. Process-input and path-policy principles are cross-platform, while API claims are explicitly Linux/POSIX-oriented. No Windows token, ACL, object-manager or named-pipe equivalence is claimed.

| ID and skill location | Primary source and locator | Supported decision and limit |
| --- | --- | --- |
| OS-1: checked name versus object; `filesystem-resolution.md` | [Linux access(2)](https://man7.org/linux/man-pages/man2/access.2.html), NOTES | A prior pathname check can be invalid for a later operation. A race still requires a feasible competing writer. |
| OS-2: constrained resolution; `filesystem-resolution.md` | [Linux openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html), DESCRIPTION and `RESOLVE_*` | Resolution flags can constrain lookup. Verify exact flags; a handle or final-component no-follow alone is not equivalent. |
| OS-3: process credentials; `process-authority-inheritance.md` | [credentials(7)](https://man7.org/linux/man-pages/man7/credentials.7.html); [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html), DESCRIPTION | Establish real/effective/saved IDs, groups and exec transitions. A nominal privilege drop does not prove authority removal. |
| OS-4: inherited state; `process-authority-inheritance.md` | `execve(2)`, Effect on process attributes and NOTES | Verify preserved descriptors and environment, including close-on-exec. A fixed executable does not establish safe inheritance. |
| OS-5: local IPC identity; `local-ipc.md` | [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), pathname permissions, abstract sockets and `SO_PEERCRED` | Abstract sockets lack pathname permission controls. “Local” does not imply trusted. |
| OS-6: restriction scope; `process-authority-inheritance.md` | [Linux no_new_privs](https://docs.kernel.org/userspace-api/no_new_privs.html), guarantees and limits | `no_new_privs` blocks specific exec-time gains; it is not a complete sandbox. |
| OS-7: command and argument interpretation; `process-execution-input.md` | [OWASP OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html), “Argument Injection” and defense options; [CWE-78](https://cwe.mitre.org/data/definitions/78.html) | Avoiding a shell removes shell parsing but does not make attacker-selected executable names, flags, configuration or other child-parser semantics safe. Confirm the actual child grammar and an authority boundary. |
| OS-8: single-element option syntax; `process-execution-input.md` | [Python 3.14 argparse](https://docs.python.org/3.14/library/argparse.html), option value syntax | A single `--flag=value` argv element can be an option under Python `argparse`. This supports the fixture and is not a claim about every child parser. |
| OS-9: path containment; `filesystem-path-policy.md` | [CWE-22](https://cwe.mitre.org/data/definitions/22.html), Description and mitigations; [CWE-73](https://cwe.mitre.org/data/definitions/73.html), Description | Trace attacker-controlled path components to the actual filesystem operation and its containment policy. String joining or a path-shaped value alone is insufficient. |
| OS-10: archive entries; `filesystem-path-policy.md` | [SEI CERT IDS04-J](https://wiki.sei.cmu.edu/confluence/display/java/IDS04-J.+Safely+extract+files+from+ZipInputStream), compliant solution | Extraction must keep entries within the destination and account for extraction behavior. Apply platform and archive-library semantics; do not infer exploitability from an archive API alone. |
| OS-11: Windows naming and reparse points; `windows-filesystem-authority.md` | [Microsoft Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file); [Reparse Point Tags](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags); [`CreateFile`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea), `FILE_FLAG_OPEN_REPARSE_POINT` | Path syntax and reparse traversal determine the opened object. The flag can open a reparse point itself in supported modes; it is not claimed to confine every intermediate component. |
| OS-12: Windows object authorization; `windows-filesystem-authority.md` | [Microsoft Access Control Model](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-model); [`AccessCheck`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-accesscheck) | Authorization depends on a token, security descriptor and requested rights. A directory name or prior string check does not replace the enforcing access check. |
| OS-13: Windows process token; `windows-process-authority.md` | [`CreateProcessAsUser`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw); [Process Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights) | Establish the primary token and granted rights. A nominal account change is not proof that all inherited capabilities were removed. |
| OS-14: Windows handle inheritance; `windows-process-authority.md` | [Handle Inheritance](https://learn.microsoft.com/en-us/windows/win32/sysinfo/handle-inheritance); [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | Trace `bInheritHandles`, inheritable handles and explicit handle lists. Version-specific exceptions require the repository's target platform. |

| OS-15: Windows named-pipe access and impersonation; `windows-services-local-ipc.md` | [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights); [Impersonating a Named Pipe Client](https://learn.microsoft.com/en-us/windows/win32/ipc/impersonating-a-named-pipe-client) | Pipe ACLs, client tokens and impersonation level control different boundaries. Verify `RevertToSelf` on every path; “local” or LocalSystem alone does not establish caller trust. |
| OS-16: Windows service authority; `windows-services-local-ipc.md` | [Service Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights); [Service User Accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts) | Service process identity differs from permissions on the service object. Report a concrete dangerous right such as attacker-controlled configuration, not merely use of a privileged account. |

Project policy requires a concrete unauthorized operation, retained capability or identity-confusion path. Missing sandbox hardening alone remains non-confirmed.

Behavior cases for the added rules: `windows-reparse-contained-open`, `windows-inherited-privileged-handle`, `windows-pipe-impersonation-retained`, `windows-pipe-authorized-client`, `boundary-web-download-path`, and `boundary-ci-script-process`. Existing path and process cases cover positive, counterexample and unknown authority conditions for the cross-platform references.

## Coverage and exclusions

Current coverage: process-input semantics, filesystem path containment, Linux pathname resolution, process credentials and exec inheritance, Unix-domain socket permissions and peer identity, and focused Windows filesystem, process, service and named-pipe authority. AppContainer, namespaces, seccomp, capabilities and mandatory-access-control details remain platform policy packs rather than generic references. Container-escape catalogs and live platform default matrices are excluded because they age quickly.
