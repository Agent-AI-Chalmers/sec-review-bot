# Parser And Protocol Security Source Notes

The sources cover interpretation boundaries and selected parser capabilities, not every format or protocol. Defaults must match the repository's library and version.

| ID and skill location | Primary source and locator | Supported decision and limit |
| --- | --- | --- |
| PARSE-1: representation agreement; `representation-boundaries.md` | [MITRE CWE-20](https://cwe.mitre.org/data/definitions/20.html), Potential Mitigations and canonicalization guidance | Validation must apply to the representation consumed. This does not prescribe repeated canonicalization or one universal form. |
| PARSE-2: HTTP/1.1 length; `http-framing.md` | [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html), §6.3 | Recipients must determine body length consistently. Apply only to HTTP/1.1 and relevant downgrade paths. |
| PARSE-3: smuggling impact; `http-framing.md` | RFC 9112, §11.2 | Differential parsing can leave bytes for another request. Conflicting headers alone are insufficient without recipient disagreement and connection behavior. |
| PARSE-4: XML resources; `parser-capabilities.md` | [OWASP XXE Prevention](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html), examples and parser guidance | External resource resolution differs from expansion and object construction. Actual defaults are parser/version-specific. |
| PARSE-5: context substitution; `representation-boundaries.md` | [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), §§2.7-2.8 and 3.8-3.12 | Integrity does not establish audience or token type. This is not a universal replay/state checklist. |
| PARSE-6: object construction versus data parsing; `object-construction.md` | [OWASP Deserialization](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html), language-specific prevention sections; [CWE-502](https://cwe.mitre.org/data/definitions/502.html) | Identify reachable types, constructors or hooks and a concrete security effect. A format name or parser API alone is only a lead; runtime gadget availability and defaults need repository/library evidence. |
| PARSE-7: guard scope; `object-construction.md` | OWASP Deserialization Cheat Sheet, language-specific prevention sections | Data-only parsing, type allowlists, schemas and signatures address different mechanisms. Verify that the control covers the same bytes and object-construction path. |
| PARSE-8: YAML constructors and safe loading; `object-construction.md` | [PyYAML Documentation](https://pyyaml.org/wiki/PyYAMLDocumentation), constructors, `safe_load` and `SafeLoader` | YAML tags and constructors can select language objects; a data-only safe loader is a counterexample. Verify the installed library/version and later consumers. |
| PARSE-9: JSON polymorphic typing; `object-construction.md` | [Jackson Polymorphic Deserialization](https://github.com/FasterXML/jackson-docs/wiki/JacksonPolymorphicDeserialization), type identifiers, default typing and security notes | JSON remains data-only unless configured metadata/resolvers construct application types. Allowed types and defaults are version/configuration-specific. |
| PARSE-10: archive-controlled structure; `archive-semantics.md` | [Python tarfile extraction filters](https://docs.python.org/3/library/tarfile.html#extraction-filters); [SEI CERT IDS04-J](https://wiki.sei.cmu.edu/confluence/display/java/IDS04-J.+Safely+extract+files+from+ZipInputStream) | Member names, links, types, metadata and order can alter extraction. Filters are library/version-specific; path authority after acceptance remains owned by OS security. |
| PARSE-11: expression structure versus data; `expression-interpreters.md` | [OWASP Expression Language Injection](https://owasp.org/www-community/vulnerabilities/Expression_Language_Injection); the reviewed engine's grammar/API documentation | Report attacker control of executable structure or enabled capabilities, not merely attacker values passed to a fixed expression. Engine names and delimiters alone are insufficient. |
| PARSE-12: HTTP/2 malformed messages; `http2-translation.md` | [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html), §§8.2.1, 8.2.3 and 8.2.4 | HTTP/2 recipients and processing intermediaries must reject defined malformed requests rather than forward them. Apply the exact pseudo-header, field and length rules; HTTP/2 presence alone is not a finding. |
| PARSE-13: HTTP/2-to-HTTP/1 translation; `http2-translation.md` | RFC 9113, §§8.2.1 and 11.1; [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), field parsing requirements | A translator must not turn invalid HTTP/2 field data into a different HTTP/1.1 message. Require a concrete unsafe translation and downstream disagreement or cross-request effect. |

Format names, malformed input and parser API presence are leads. Confirmation requires attacker input, enabled interpretation/capability, an ineffective guard and concrete effect.
