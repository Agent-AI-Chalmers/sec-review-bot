# Agent Trajectory v1

Language: [English](SPEC.md) | 中文

Trajectory 记录一次 Agent 执行，供检查、Memory 提取和用量核算使用。它保存消息、来源和执行关系，不依赖某个 Agent 框架或可观测性服务。

[记录 schema](schemas/record.schema.json)定义结构要求。[Corpus manifest](corpus/manifest.json)定义共同的接受用例。

## 文件与记录格式

Trajectory 使用 UTF-8 JSONL：每行一个 JSON 对象。消息正文中的换行转义保存在对象内。每条记录包含正整数 `seq` 和事件名 `event`。序号在同一文件内递增，不要求连续。

记录以 LF（`U+000A`）分隔，也接受 CRLF。JSON 字符串中的 `U+0085`、`U+2028`、`U+2029` 等 Unicode 分隔符属于内容，不是记录边界。

消息使用 `event: "message"`。外层记录保存来源和执行关系，`message` 保存消息本身。生产端写出一种规范表示。读取端在使用记录前校验格式。

## 消息与来源

| 字段                   | 含义                                                                       |
| ---------------------- | -------------------------------------------------------------------------- |
| `message.id`           | 消息身份，在 trajectory 内唯一；同一消息被多次观察时保持该身份，只记录一次 |
| `message.role`         | `system`、`user`、`assistant` 或 `tool`                                    |
| `message.content`      | 原始文本或结构化内容块；内容块的 `type` 描述内容种类，不表示消息角色       |
| `agent`                | 消息所属对话或执行分支的 Agent，已知时提供                                 |
| `source`               | 消息来源或用途，已知时提供；`summarization` 标识摘要相关材料               |
| `call_id`              | 生成该响应的模型调用，适用时提供                                           |
| `run_id`、`parent_ids` | 执行身份，以及从根到直接父执行的有序祖先关系，可用时提供                   |

不同生产端的 `agent` 和 `source` 含义一致。框架特有的元数据可以作为附加证据保留，但读取端不需要依赖它来解释这些字段。缺少标签表示来源未知，不默认归属于根 Agent。

保留可获得的工具状态、结构化结果、推理内容和其他消息数据，不用面向展示的渲染结果替换原始内容。预览格式不改变存储内容，也不改变复制时提供的原文。

## 顺序与对话上下文

`seq` 表示平铺阅读顺序。能够获得初始 system 指令时，将其放在该 Agent 的 user 输入之前，随后记录回复和工具交互。变更后的 system 指令出现在使用它的调用之前。并发 Subagent 可以交错出现，通过来源和祖先关系区分分支。

Trajectory 是执行历史，不是每次模型调用的完整请求快照。只保存一次的消息可能被多个请求使用。仅凭序号不能确定某次请求包含哪些消息，也不能认为不同 Agent 共享同一上下文。

保留已观察到的历史，即使它后来被移出活动对话或被摘要替换。执行在获得 system 指令前终止时，不虚构该指令。

- **Subagent**：保留可获得的指令、输入、回复和工具交互，并标明其自身来源与执行祖先关系。
- **Summarization middleware**：保留摘要请求和模型响应，包括可获得的 usage。同时保留写入后续对话的摘要；它是用途不同的另一条消息。
- **摘要解释**：摘要是可能出错的导航辅助，不是独立证据或新的用户指令。原始证据仍应保留，供核对使用。

## 模型调用与工具交互

| 事件                | 含义                                                        |
| ------------------- | ----------------------------------------------------------- |
| `model_calls_start` | 开始记录本次执行的模型调用                                  |
| `model_call_start`  | 开始一次模型调用，由 `call_id` 标识                         |
| `model_call_end`    | 该调用成功返回；`message_id` 引用其响应消息                 |
| `model_calls_end`   | 记录结束，执行状态为 `completed`、`failed` 或 `interrupted` |

响应以消息形式保存一次。调用结束记录引用它，不重复保存响应或 usage。失败或中断的调用可能只有开始记录，没有结束记录；不要为其补造成功响应。

模型调用 ID 在 trajectory 内标识调用。工具请求使用 `message.tool_calls[].id`，工具结果使用 `message.tool_call_id`。工具 ID 在执行分支内关联请求和结果，不替代模型调用 ID 或执行祖先关系。现有关系不足以消除歧义时，保留未关联状态，不任意选择一个结果。

下面的简化示例展示一次已完成的调用：

```jsonl
{"seq":1,"event":"model_calls_start"}
{"seq":2,"event":"message","agent":"reviewer","message":{"id":"s1","role":"system","content":"Review the change."}}
{"seq":3,"event":"message","agent":"reviewer","message":{"id":"u1","role":"user","content":"Inspect the patch."}}
{"seq":4,"event":"model_call_start","call_id":"c1","agent":"reviewer"}
{"seq":5,"event":"message","call_id":"c1","agent":"reviewer","message":{"id":"a1","role":"assistant","content":"A check is needed.","usage_metadata":{"input_tokens":10,"output_tokens":2,"total_tokens":12,"cache_read_input_tokens":null,"cache_creation_input_tokens":null,"reasoning_tokens":null}}}
{"seq":6,"event":"model_call_end","call_id":"c1","message_id":"a1"}
{"seq":7,"event":"model_calls_end","status":"completed"}
```

## 用量与完整性

消息的 `usage_metadata` 描述生成该响应的模型调用。对每次已观察到的调用最多统计一次；存在调用结束记录时，使用其引用的响应。缺少调用结束记录时，可以计入无歧义的已记录响应用量，但这不证明调用成功完成。作为上下文传入的历史消息不构成新调用。重新读取其内容的消耗，已包含在新调用报告的输入用量中。

`message.usage_metadata` 是标准化的逐调用 token 记录，与信封层 `metadata` 不同。无法获得时可以省略或设为 `null`。非 null 对象必须恰好包含以下字段；每个值为非负安全整数或 `null`。缺失的测量值使用 `null`，不当作零；明确报告的零保留为 `0`。

本契约遵循 OpenTelemetry GenAI 的 token 统计语义：输入/输出采用包含式总量，缓存和推理作为子集。JSON 字段名及记录结构由本项目定义，不照搬 OpenTelemetry 的属性名或指标名。OpenTelemetry GenAI 规范独立演进；上游命名变化不会自动改变本契约。生产端负责将来源词汇映射为下表定义的字段。

| 字段                          | 含义                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| `input_tokens`                | 包含缓存读取和缓存写入的输入总量                                                           |
| `output_tokens`               | 包含推理的输出总量                                                                         |
| `total_tokens`                | `input_tokens` 与 `output_tokens` 均已知时为 `input_tokens + output_tokens`，否则为 `null` |
| `cache_read_input_tokens`     | 输入中的缓存读取子集                                                                       |
| `cache_creation_input_tokens` | 输入中的缓存写入子集，与缓存读取不重叠                                                     |
| `reasoning_tokens`            | 输出中的推理子集                                                                           |

已知缓存子集之和不能超过已知输入；已知推理量不能超过已知输出。消费端拒绝不可能的子集、不一致的总量、非 null 用量对象缺少字段，以及标准用量内的框架专用详情字段。计数上限为 `9007199254740991`，保证 Python/JavaScript 互操作。缓存和推理是子集，不得额外加到包含式总量上。

生产端在适配边界完成归一化。LangChain 总量和 OpenAI prompt/completion 总量已经采用包含式口径。Anthropic 普通输入不含单独报告的缓存桶，需加一次。Langfuse 普通输入/输出桶不含缓存/推理桶，需加一次。缺失的可选桶不增加该适配口径下的总量，但不能据此将对应子集记为已上报零值。普通桶缺失时，其包含式总量保持未知。`total_tokens` 从归一化后的分量计算；源总量冲突时发出警告，原始供应商观测数据保留在标准用量之外。只有源 total 不足以确定 input/output 或标准 total。

消费端读取标准用量，不解释供应商元数据或 LangChain 详情映射。只有覆盖范围内每次调用都具有某字段的已知值时，才能汇总该字段；否则该字段的汇总保持未知。没有观测到调用时，总量未知。部分和作为下界时可以单独展示并明确标注，不能当作完整总量。未缓存输入和比率所需的任意操作数未知时，派生值保持未知。完整用量核算要求调用记录已结束，且每次覆盖调用的六个字段均已知；仅 input/output 已知不足以证明缓存或推理覆盖完整。

Agent 运行时负责框架/供应商转换及轨迹用量校验。仓库脚本负责运行目录发现、工作流相关的有效补丁路径选择和报告渲染。Langfuse 查询代码负责其外部数据源转换，归一化后的字段含义与本契约及 Review Runs token 总量一致。

运行级汇总用量放在独立 metrics 产物或明确区分的汇总记录中，不附到某条响应上。只能获得汇总用量时，保留该汇总，不虚构逐调用分配。

评估完整性时，在声明的观测范围内区分以下结论：

- **执行完成**：Agent 执行正常结束。
- **调用记录完整**：声明的执行范围内，所有模型调用都被采集，包括 Subagent 和摘要调用。
- **用量完整**：调用记录完整，且每次调用都有所需的报告用量。

单凭完成标记不能证明调用或用量完整。核算报告说明已知的覆盖限制，例如用量缺失、调用未结束或终止标记缺失。可以报告已知总量而不声称用量完整；不要求消费端发现其观测范围之外的调用。

## 不完整轨迹与外部轨迹

外部生产端可能无法提供 system 指令、调用边界、祖先关系或逐调用用量。保留其实际提供的内容，将无法获得的信息视为未知；可读消息仍有使用价值，但不足以证明核算完整。

读取端拒绝格式损坏的 JSONL 和违反规范的记录。中断轨迹中的记录均符合格式时仍可读取。核算报告区分已知用量与完整核算的声明。引用不一致的记录不能被视为核算完整。任何消费端都不应仅凭工具请求、在没有结果时推断执行成功。

## 整体文件规则

输入为 UTF-8 JSONL，每个非空行是一条记录。序号为正的安全整数，并严格递增。消息 ID 在文件内唯一。可选的附加数据保留，但不改变已定义字段的含义。

提供调用生命周期事件时，记录以 `model_calls_start` 开始。每次模型调用开始具有不同的 `call_id`。调用结束位于开始之后，引用已经记录且具有相同 `call_id` 的响应。执行记录结束位于记录开始之后，其后没有其他记录。未结束的记录是有效输入，但执行覆盖不完整。

纯消息轨迹有效，但不能证明模型调用覆盖完整。不得修补或推断记录，将无效文件转为有效。

`metadata` 是可选的 JSON 对象，保存附加观测信息。它不定义消息身份、角色、来源、调用关系或用量。标准顶层字段和 `message` 字段是解释依据，消费端不得从元数据补齐这些字段。生产端可以原样保留观测信息；元数据内部字段不属于契约。

## 生产端与消费端义务

生产端写出规范的消息角色和来源字段，保留原始内容，每条消息只记录一次。逐调用用量属于产生该消耗的响应。运行汇总独立于响应用量。

消费端在使用前校验收到的文件。无效输入产生明确错误；缺少可选信息本身不使 trajectory 无效。

消费端义务取决于用途。展示端可以提取消息和已记录用量，无需评估执行或核算是否完整。核算端保留计算所需的执行记录，并说明已知的覆盖限制。两类消费端都不得推断缺失事实，也不得作出超出已有证据的完整性声明。
