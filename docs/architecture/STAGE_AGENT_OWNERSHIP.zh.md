# Stage、agent 与资源生命周期

语言：[English](STAGE_AGENT_OWNERSHIP.md) | 中文

本文是 [STAGE_AGENT_OWNERSHIP.md](STAGE_AGENT_OWNERSHIP.md) 的中文译文。英文版是权威版本；如果两者不一致，以英文版为准。

这份项目使用大模型检查代码、提出修复，并把结果交给后续流程。一次这样的任务，除了调用模型，还需要准备代码文件、提供工具、保存结果和清理临时环境。本文解释这些工作为什么分在 stage 和 agent 两处，以及写代码时怎样决定由谁负责。

下面先用“修复一处代码问题”说明概念。这是帮助理解分工的例子，不要求每个阶段都执行同样的步骤。

## 先看一次修复如何完成

假设上游已经提供了问题说明和一份待修复代码。接下来需要做这些事：

1. 创建临时目录，把待修复代码放进去。
2. 给模型提供问题说明，以及读取、修改代码所需的工具。
3. 让模型检查代码、调用工具修改文件，并返回修复说明。
4. 从修改后的文件生成补丁，保存说明和补丁，供后续验证或交付使用。
5. 关闭连接，清理不再需要的临时环境。

在这个例子里，**stage（阶段）是负责完成整段修复工作的程序**。它接收上游输入，安排执行，并交出后续流程能够使用的结果。分析问题、修复代码、验证修复，都可以有各自的阶段。

**agent 是其中通过模型和工具完成任务的部分**。它把提示词和工具提供给模型，让模型根据工具返回的信息继续工作，最终取得结果。

所以，模型完成修复并返回说明时，agent 的执行可以结束，**但修复阶段还没有结束**：stage 仍需要提取补丁并保存产物。这就是 stage 和 agent 的主要区别。

## 代码里的几个名称

阅读相关代码时，还会遇到这些名称。最后一列沿用同一个示例：修复 `app.py` 中缺少输入检查的问题。示例中的文件名和路径仅用于说明。

| 名称 | 本文中的含义 | 同一次修复中的例子 |
| --- | --- | --- |
| agent 调用入口 | 调用方用来运行 agent 并取得结果的函数。它可以负责准备工具和调用模型，不要求定义一个 agent 类。 | stage 调用修复入口，把问题说明和已准备好的 backend 传进去，等待修复结果。 |
| graph | LangGraph 把模型调用、工具执行等步骤组织起来形成的可执行流程。`CompiledStateGraph` 是编译后可执行的 graph 对象；创建这个对象不等于已经运行了 agent。 | 修复入口构建 graph，由它安排模型读取 `app.py`、调用编辑工具、返回修复说明。 |
| backend | 工具访问文件或执行命令所用的接口。它决定工具能够访问哪个工作区、在什么环境中操作；这里不是指项目的后端服务。 | graph 中的文件工具通过 backend 访问临时工作区里的 `app.py`。 |
| middleware | 在模型或工具执行前后插入处理逻辑的代码，例如补充上下文或检查结果。 | 执行时，middleware 把项目要求加入模型上下文，例如要求补上输入检查的测试。 |
| memory view | 提供给本次执行使用的经验记忆文件视图，用于让 agent 读取已有经验。它不是模型在进程中的运行内存。 | 模型通过文件工具读取 memory view 中的经验，了解该项目处理输入检查时的注意事项。 |
| 产物 | 后续步骤需要使用的输出，例如补丁文件、审查结果和执行记录。 | agent 返回后，stage 从 `app.py` 的修改生成 `workspace.patch`，连同修复说明保存。 |

这些名称描述不同的东西：stage 表达业务步骤，agent 表达模型如何完成任务，graph 是执行 agent 的一种技术形式。它们不要求一一对应成类或对象。

## 从要完成的事情划分职责，而非资源管理

stage 负责准备业务输入、安排 agent 执行和处理业务结果。agent 负责提示词、工具、模型执行及输出格式等细节。stage 不必了解 agent 内部每个工具如何连接，agent 也不必知道补丁最终要交给哪个后续阶段。

“资源”指使用期间需要保持可用、结束后需要清理的东西，例如临时目录、连接和进程。“生命周期”就是从创建或取得它，到关闭或释放它的这段时间。本文说某段代码“拥有”资源，指它负责安排这段时间，并在出错时也做好清理。另一段代码可以借用资源，而不负责关闭它。

资源管理跟随业务职责。不要先把 stage 定义成“资源准备层”，再把所有需要清理的东西都塞进去。下面分别看工作区和 MCP 会话为什么适合放在不同位置。

## 工作区为什么通常由 stage 管理

以生成补丁为例，工作区的使用过程可以是：

```text
创建工作区 → 恢复输入快照 → agent 修改文件 → 提取补丁、保存产物 → 删除工作区
```

agent 返回后，stage 还要读取文件。工作区应覆盖这个完整过程，由 stage 管理更合适。agent 借用可访问工作区的 backend，调用结束时不负责销毁外部提供的 backend。

backend 和 memory view 也应按实际使用范围判断。某项资源由 stage 提供，不代表 agent 可以决定它何时关闭；某项资源仅供一次 agent 调用使用，也不必为了统一写法而移到 stage。

## MCP 会话为什么适合由 agent 调用入口管理

MCP（Model Context Protocol）是程序与工具服务通信的一种协议。例如，agent 可以通过 MCP 使用另一个进程提供的代码查询工具。模型看到的是可调用的工具，程序需要在背后建立连接、发送请求并读取结果。

会话是这段通信中保持连接和状态的上下文。需要管理生命周期的是会话、连接，以及可能随连接启动的进程。加载出的工具可能绑定着会话；如果提前关闭会话，即使还保留着工具对象，也无法保证继续调用它。

agent 知道自己需要哪些 MCP 能力。对于仅供本次调用使用的会话，agent 调用入口适合负责打开会话、加载工具、构建和执行 graph，并在结束时关闭会话。底层 MCP helper 负责具体的连接和清理机制。正常返回、异常和取消都需要考虑。

stage 提供 backend 等执行条件，接收 agent 的结果，无需接触 MCP 的传输配置和会话管理。这样的分工允许 stage 管理更长的业务过程，同时让 agent 管理自己的工具使用过程。
