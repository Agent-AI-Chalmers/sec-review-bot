# Trusted Setup

语言：[English](TRUSTED_SETUP.md) | 中文

本文是 [TRUSTED_SETUP.md](TRUSTED_SETUP.md) 的中文译文。英文版是权威版本；如果两者不一致，以英文版为准。

仓库可以在**默认分支**上声明如何准备它被审查时所用的环境。本页记录这个功能**为什么**是现在这个样子：它要解决什么问题、由此引出什么信任问题、信任模型推出哪些约束，以及哪些选择与信任无关。

声明的格式是一份独立契约：[contracts/setup-declaration](../../contracts/setup-declaration/README.zh.md)。

## 问题

agent 在一个 Docker 沙箱里审查仓库，而沙箱镜像**不含**该仓库的依赖。实际表现就是不确定：agent 要么放弃、凭记忆猜；要么临时从公网冷装依赖——慢、装不全（缺 `uv`、Python 版本还对不上）、时好时坏。

显然的修法是：让仓库自己声明如何准备环境，并在 agent 启动前执行这份声明。但这个修法带来了真正的问题：**声明是仓库提供的可执行内容**，于是"怎么装依赖"立刻变成"我们到底多大程度相信仓库递过来的东西？"。本设计的其余内容，都是对这个问题的回答。

## 信任问题

信任不是开/关那么简单；它是**稀缺的**，要按来源分别分配。整个设计的形态，都来自"对每个能触及沙箱的来源，信到什么程度、这份信任换来什么权限"的判断。

| 来源 | 为什么是这个位置 | 由此推出的约束 |
| --- | --- | --- |
| 默认分支（维护者已合并的内容） | 经过 review 与合并；仓库的受控面 | 声明的**唯一**合法来源 |
| PR head / fork | 作者可任意改，且尚未合并 | 绝不作为声明来源；外部 fork 需显式批准 |
| webhook payload | 它可以指向任意分支 | 绝不作为受信 ref 的来源 |
| 声明的内容 | 是可执行内容 | 严格白名单；最小权限；隔离执行 |
| 网络 | 不可信代码可能滥用它 | 基线由部署方定；仓库或 fork 只能收紧 |

把"约束"这一列读下来，本设计余下的部分就已经浮现了。

## 信任模型如何落地

### 声明只来自默认分支

默认分支是维护者唯一 review 并合并过的版本，因此也是唯一允许提供可执行内容的版本。两条规则保证这一点：

- **默认分支一律走 API 解析，绝不来自 payload。** 每个入口——issue、pull request、repository——都用仓库自身的身份调用 GitHub 解析 `{default_branch, head_sha}`；webhook payload 字段永远不是来源，解析失败即运行失败。payload 可以指向任意分支，"payload 里分支 X 的 SHA"并不能证明"X 是默认分支"。
- **对 pull request，用 base 仓库。** 身份是 base 仓库（`base_repo_full_name`），绝不是 head/fork。PR 的 workspace 检出在 head，作者可改；它不能有能力改变将要运行的声明。

被否决的替代方案是 API 优先、payload 兜底——兜底是 *假受信*，会悄悄降级到不可信来源。（从 workspace 或 head 仓库读声明，同理被否决。）

这不是自创的规则：GitHub Copilot 自己的 setup steps 同样必须来自默认分支。信任推理完全一致，本设计守住同一条线。

### fork 是陌生人

对 fork 代码的自动 review，与"围绕受信仓库可控范围构建"的信任模型不符。

fork PR 事件（`opened`、`ready_for_review`、`synchronize`）一律跳过。维护者评论 `@<bot> review` 表示批准，复用现有的 `write` 权限校验。批准是按次的：每条评论各自发起一次 review，不会被保存或复用，因此先前的批准永远不会授权后来的 review。

GitHub 对 fork 的首次运行也要批准，但它的批准信号多且语义各异。本系统的隔离手段更少，因此只设一种明确、按次的批准方式。

无论如何，声明仍来自 base 默认分支，网络基线也由部署方决定——所以 fork 既改不了将要运行的东西，也改不了它能触达的范围。注意 `from_fork` 不等于"恶意"（同 org 的 fork 仍是 fork），因此它只用于要求一次显式批准，绝不用于放宽任何规则。

### 因为信不过，所以隔离

声明可以联网，而且它可能带有恶意。这一切之所以安全，只因为有一条隔离基线——每个 run/stage 一个容器（唯一命名、`--rm`）、容器环境为空（不注入任何跨仓库凭据）、最小挂载（只挂视图声明的路径；App 私钥这类单个文件根本挂不进去，因为挂载只接受目录）、跨仓库凭据 / App 私钥永不进入容器。这与托管 CI runner"默认联网、靠每 job 隔离而非断网"的模型同构。

被否决的替代方案是永久 `--network none` 的沙箱 + 宿主侧"填充器"缓存池。既然有网可用，这套机制就不需要了；本设计把 `none` 保留为 *默认值*、把基线做成 *可配置*，安全性来自隔离基线，而不是硬编码的断网。

### 网络权限属于部署方，不属于仓库

联网基线由**部署方**设定（`AGENT_DOCKER_NETWORK_MODE`，默认 `none`）。仓库和 fork 都无法改变它。仓库是被信任的一方，而不是授予信任的一方：它不能给自己超出部署所允许的网络权限。

## 其他设计选择

以下决定很重要，但它们不是信任判断。它们关系到环境如何取得、声明如何定义，而不关系到每个来源被信到什么程度。放在这里，是为了不把它们和上文的信任模型混为一谈。

**不把依赖烤进镜像。** workspace 镜像只作"隔离宿主 + 通用引擎"，不预装被测仓库的依赖。工具链组合（语言 × 框架 × 仓库）无穷无尽，预判必然失败——"今天装 uv，明天装什么？"。

**不在 CI 里跑 agent。** 长跑 agent 在自己的容器里运行，不进 GitHub Actions。CI 额度有限，一次带冷装的 review 撑不起。（托管 CI 的 *信任* 模型被复用——见上文"隔离"；它的 *执行* 模型没有。）

**用自定义声明文件，不用 CI 生态的文件。** 声明位于 `.sec-review/setup.yml`。具体到最值得点名的那种替代方案，就是复用 CI 生态已有的文件——GitHub Copilot 的 `.github/workflows/copilot-setup-steps.yml`。它被否决：格式不归我们掌控；读它就得解析 Actions YAML、只抽 `run` 步骤、还要处理 `uses:`——为了一个不属于我们的格式，引入更多复杂度。

**声明是每个 stage 各跑一次，而不是每个 run 只跑一次。** 每个 review stage 都有自己的 sandbox，因此声明会在每个实际执行的 stage 开头执行一次（analysis、mitigation、verification），仓库审查下还会为每个 case 再执行一次。这是 per-stage 容器隔离的代价——跨 sandbox 没有共享缓存，而引入共享缓存会重新打开隔离基线已经关上的信任与污染问题。因此声明应当幂等且尽量快；单步 timeout 上限（`SEC_REVIEW_SETUP_STEP_MAX_SECONDS`）约束的是单次执行，而不是执行次数。

**不猜安装命令。** 没有 lockfile 启发式，也没有"仅探测 + 提示"；只有显式声明才驱动重建。启发式在多语言 monorepo、私有 registry、混合工具链上必然误判（本仓库自己就是 uv + pnpm + npm + cargo），而按惯例推断会从一份我们并未为此审查过的仓库里自动执行安装脚本。被否决的替代方案是默认开启的按惯例推断兜底，以及"探测 + 提示"。接受的后果：没有声明的仓库得到空环境。
