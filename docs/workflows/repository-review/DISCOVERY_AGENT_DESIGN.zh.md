# Discovery Agent 设计原则

语言：[English](DISCOVERY_AGENT_DESIGN.md) | 中文

本文是 [DISCOVERY_AGENT_DESIGN.md](DISCOVERY_AGENT_DESIGN.md) 的中文译文。英文版是权威版本；如果两者不一致，以英文版为准。

## 定位

Discovery 是 repository review 的初筛阶段。它的目标是在成本可控、覆盖可解释的前提下，尽可能早地找出值得进一步分析的安全线索。

这一阶段产出的是 candidate，而不是漏洞结论。Candidate 应当有具体的仓库位置、可疑行为和初步证据，但可以存在不确定性。后续由 triage 判断 candidate 应该保留、抑制还是合并，再由 analyzer 根据更完整的上下文确认或否定问题。

Discovery 因此不承担漏洞定性、`vulnerability_type` / CWE 分类、跨文件根因合并或最终报告生成。它也不试图让一个 agent 自由探索并理解整个仓库，而是在明确的文件范围和局部上下文中进行可重复的筛查。

## 扫描范围

Discovery 关注可能直接承载程序行为或安全边界的文件。“能够作为 UTF-8 文本读取”并不自动意味着文件值得进入初筛。扫描范围由三层边界共同决定。

### `paths_ignore`

`paths_ignore` 表达仓库维护者的显式排除意图。它属于这次扫描的仓库范围设置，与项目默认的文件类型策略不同。

### 文件类型策略

文件选择采用黑名单，而不是编程语言白名单。代码库可能包含小众语言、DSL、无扩展名脚本或项目自定义格式；如果只扫描预先列出的语言，遗漏会随着代码库类型变化而不断增加。因此，未知扩展名和无扩展名的可读文本默认保留。

以下文件默认不作为 discovery 起点：

- Markdown 和 reStructuredText：`.md`、`.rst`；
- 普通文本：`.txt`、`.text`；
- 表格数据：`.csv`、`.tsv`；
- 日志：`.log`。

这是一项输入选择策略，而不是读取能力限制。这些文件仍可能在后续阶段成为有用上下文，但前提是已经存在具体 candidate 和明确的读取目标。

文档文件不会仅仅因为名为 `SECURITY.md`、`threat-model.md` 等就进入 discovery。文件名只能暗示主题，不能证明文档与某段代码或安全行为有关。只有将来存在可靠的代码关联机制，能够从代码、构建配置或显式依赖建立这种联系时，才应重新考虑文档边界。

YAML、JSON、SQL、XML 和 HTML 保持扫描。它们既可能是普通数据，也可能直接描述部署、权限、策略、查询、模板或数据边界；仅凭扩展名排除会损失真实的安全覆盖。

扫描结果应让读者能够区分主动忽略、类型策略排除、资源限制以及文件不可读，而不是把它们都解释为“未扫描”。

### 单文件大小保护

Discovery 在读取文件之前使用 `AGENT_DISCOVERY_MAX_FILE_BYTES` 限制单文件字节数，默认值为 256 KiB。它是 worker 读取、解码和 prompt 构造的资源边界，不是模型上下文边界；字节数与 token 数之间没有稳定换算关系，超过该限制并不表示模型一定装不下文件。

这个限制属于服务运行环境，而不属于单次 review 的扫描范围。它不在公开 `scan_scope` 契约中，调用方不能为某次请求放宽 worker 的安全边界。当前没有证据支持调整 256 KiB 默认值，只有发现值得扫描的源文件确实因此被排除时，才应结合具体样本和资源成本重新评估。

## Chunk 设计

Discovery 的输入组织有两种直接方案。

方案 A 是让每个 discovery agent 只读取一个文件。它的优点是注意力集中，每次调用的代码范围也非常明确。代价是每个文件都需要一次独立的模型调用，并重复加载 system prompt、输出 schema 和其他固定上下文。对于包含大量小文件的仓库，这部分固定开销可能显著增加成本；单文件视角也无法直接提供局部的跨文件关系。

方案 B 是先把若干文件组成 chunk，再让每个 discovery agent 处理一个 chunk。它可以分摊固定 prompt 的成本，并保留一定的跨文件上下文。相应的风险是 chunk 越大，模型需要同时关注的内容越多。实验也表明，即使请求没有超过最大输入限制，过长的上下文仍可能降低安全线索的召回。

当前默认选择方案 A（`single-file`），让每次模型调用都有明确且集中的代码范围。方案 B（`batched`）仍可通过 worker 侧部署配置 `AGENT_DISCOVERY_CHUNK_STRATEGY` 启用，但不能由 review 请求选择。启用批量模式时，普通 chunk 的目标大小设为实际选定模型上下文窗口输入上限的五分之一，在调用成本和注意力之间保留明确余量。

当前采用两个不同的 token 边界：

| 输入形态 | 边界 | 行为 |
| --- | --- | --- |
| 普通多文件 chunk | 实际选定模型上下文窗口输入上限的五分之一 | 持续加入文件，直到下一个文件会超过这个 target。 |
| 单文件 chunk | 实际选定模型上下文窗口输入上限的五分之四 | 文件即使超过普通 target，仍可以独立扫描；剩余五分之一用于运行时开销。 |
| 超过单文件上限 | 超过实际选定模型上下文窗口输入上限的五分之四 | 以超过 discovery token budget 为由跳过文件。 |

五分之一只约束普通多文件 chunk，不应反过来阻止完整文件被扫描。一个文件即使超过普通 target，只要没有超过单文件 hard limit，仍作为独立 chunk；只有超过 hard limit 时才无法进入 discovery。

hard limit 会为运行时追加的 schema、skill guidance、tool turn 以及 token 估算误差预留剩余五分之一。文件保持完整，不为了满足 target 而切成片段。这样可以避免在任意位置打断局部语义，也让 candidate 的文件位置和扫描覆盖更容易解释。

所有 token 边界都基于实际选定模型的上下文窗口输入上限。Prompt 大小也按完整请求估算，包括 system prompt、user prompt、文件信息和文件内容。
