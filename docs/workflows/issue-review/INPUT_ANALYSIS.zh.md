语言：[English](INPUT_ANALYSIS.md) | 中文

## 收到 Issue 后如何开始调查

Issue 的标题和正文提供调查线索，不保证其中的判断正确。报告可能完全成立，也可能只描述了部分现象、误判根因、夸大影响，或指向已经修复的问题。

不能直接相信 Issue，也不能完全忽略它给出的方向，否则往往不知道从哪里开始查代码。例如，Issue 提到状态不一致、几个 helper 行为不同或某种 fallback 有问题，Agent 就应先沿这些线索寻找第一批代码证据。

Issue 的作用是**给出初始搜索方向**；Agent **顺着 Issue 去查，但不把它的说法当作事实**。

*本文讨论的是 `audit` 目标下的调查方式；`repair` 如何使用可信修复线索，见 [REVIEW_INTENT](../REVIEW_INTENT.zh.md)。*

## 调查中的两个风险

调查需要同时避免过早下结论和无边界扩展。

### 风险一：太早相信 Issue

Agent 很容易这样想：

- Issue 提到了几个对象、路径、helper
- 我顺着它找到了几处相关代码
- 看起来挺像
- 那应该差不多就是这个问题了

结果就是：

- 很快收敛
- 但可能收敛错了
- 把 Issue 的解释当成了事实

这种失败的本质是：**太早相信 Issue，太早相信自己找到的第一个解释**

### 风险二：为了全面而无限扩散

Agent 也可能反过来这样想：

- Issue 说 different paths
- 那我得把所有 path 都查一遍
- Issue 说 state inconsistent
- 那我得把所有 related helper 都翻一遍
- 万一还有别的相似路径呢

结果就是：一直搜、一直确认、一直不敢停，最后开始兜圈子。

这种失败的本质是：

- **怕漏，所以不停补查**
- **为了全面，失去克制**

所以 Issue 审查里的核心张力其实很简单：

- 既不能太早相信 Issue
- 也不能为了全面而无限扩散

## 调查时需要厘清什么

Agent 在调查 Issue 的时候，不应该把 Issue 正文当成一整块直接拿去用，而是要在调查过程中不断把它拆开来看。

这里不是让 Agent 脱离调查去做“静态解析”，而是：**一边查代码**，**一边校正对 Issue narrative 的理解**。

在这个过程中，Agent 至少要不断处理下面四类东西。

### 1. 它明确说了什么

这是最直接能拿来查代码的部分。

例如：

- 提到了哪些对象
- 提到了哪些状态
- 提到了哪些 helper / path / phase
- 提到了什么现象

### 2. 它暗示了什么

这些不是明说的结论，但会影响调查面。

例如：

- 既然说 `different paths`，那就不能只查一条
- 既然说 `resulting state inconsistent`，那就要看最终状态，不只是看局部调用

这些内容的作用是：提醒 Agent 调查时不要过度收窄。

### 3. 它没说清什么

这部分最危险，因为 Agent 很容易自己补。

例如：

- 到底什么才算正确状态？
- 修复后到底应该满足什么不变量？
- 哪些路径必须一致，哪些可以不同？

### 4. 它最容易让人过早下结论的地方是什么

这里不是说 Issue 在骗人，而是说：某些说法特别容易让 Agent 过早选择一个局部解释。

例如：

- 看到某个词，很容易往一个自然但错误的方向理解
- 看到一个现象，很容易把局部解释当成根因

## 一次调查的基本顺序

如果把这个过程压成一个非常简单、非常朴素的工作流，大致就是这样：

1. Issue 来了，不把它当事实，只把它当调查入口，顺着它去找第一批代码证据
2. 一边查，一边更新对 Issue 说法的判断
3. 如果发现 Issue 的说法不成立，就结束对该说法的追查，不代表直接终止整个 workflow。
4. 如果发现大方向成立，再审慎决定调查面要不要扩展
5. 整个过程中始终避免两个极端：太早相信第一个解释，以及为了全面而无限扩散
6. 最后得出结论：这个问题是否在当前代码库中成立；如果成立，证据和逻辑链是什么，形成怎样的 narrative；如果不成立，问题出在哪里。
