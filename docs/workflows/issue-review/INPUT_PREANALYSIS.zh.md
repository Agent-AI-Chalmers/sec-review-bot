## What Actually Happens When An Issue Arrives

一个 issue 来了，agent 拿到的通常只有 `title` 和 `body`。要明白：issue 不是事实，答案，只是一个带方向的输入。也就是说，agent 一开始面对的不是“已经成立的问题”，而是“别人提供的一段说法”。这段说法可能是：对的/部分对/根因说错了/影响夸大了/甚至当前代码里已经没有这个问题了。

所以 agent 的第一件事不是“修”，而是：先判断这个 issue 说的问题是不是真的，或者至少判断：它是不是一个值得继续查的线索。

但这里有一个很现实的限制：虽然不能直接信 issue，也不能完全不跟着它走。因为如果不沿着它给的说法走，往往连从哪里开始找代码都不知道。

比如 issue 说：某个状态不一致 / 某几个 helper 处理不一样 / 某种 fallback 有问题，那 agent 最好先沿着这些说法去代码里找第一批证据。

所以 issue 的作用是**给出初始搜索方向**；agent **顺着 issue 去查，但不把它的话直接当真**。

## The Two Risks: Trusting Too Fast vs Expanding Too Far

一旦 agent 开始顺着 issue 去查，很容易走到两个极端。

### 风险一：太早相信 issue

agent 很容易这样想：

- issue 提到了几个对象、路径、helper
- 我顺着它找到了几处相关代码
- 看起来挺像
- 那应该差不多就是这个问题了

结果就是：

- 很快收敛
- 但可能收敛错了
- 把 issue 的解释当成了事实

这种失败的本质是：**太早相信 issue，太早相信自己找到的第一个解释**

### 风险二：为了全面而无限扩散

agent 也可能反过来这样想：

- issue 说 different paths
- 那我得把所有 path 都查一遍
- issue 说 state inconsistent
- 那我得把所有 related helper 都翻一遍
- 万一还有别的相似路径呢

结果就是：一直搜/一直确认/一直不敢停/最后开始兜圈子

这种失败的本质是：

- **怕漏，所以不停补查**
- **为了全面，失去克制**

所以 issue-review 里的核心张力其实很简单：

- 既不能太早相信 issue
- 也不能为了全面而无限扩散

## What The Agent Must Do While Investigating

agent 在调查 issue 的时候，不应该把 issue body 当成一整块直接拿去用，而是要在调查过程中不断把它拆开来看。

这里不是让 agent 脱离调查去做“静态解析”，而是：**一边查代码**，**一边校正对 issue 叙事的理解**。

在这个过程中，agent 至少要不断处理下面四类东西。

### 1. 它明确说了什么

这是最直接能拿来查代码的部分。

例如：

- 提到了哪些对象
- 提到了哪些状态
- 提到了哪些 helper / path / phase
- 提到了什么现象

### 2. 它暗示了什么

这些不是明说的结论，但会影响调查面。

例如：

- 既然说 `different paths`，那就不能只查一条
- 既然说 `resulting state inconsistent`，那就要看最终状态，不只是看局部调用

这些内容的作用是：提醒 agent 调查时不要过度收窄

### 3. 它没说清什么

这部分最危险，因为 agent 很容易自己补。

例如：

- 到底什么才算正确状态？
- 修复后到底应该满足什么不变量？
- 哪些路径必须一致，哪些可以不同？

### 4. 它最容易让人过早下结论的地方是什么

这里不是说 issue 在骗人，而是说：某些说法特别容易让 agent 过早选择一个局部解释

例如：

- 看到某个词，很容易往一个自然但错误的方向理解
- 看到一个现象，很容易把局部解释当成根因

## A Simple Working Flow

如果把这个过程压成一个非常简单、非常朴素的工作流，大致就是这样：

1. issue 来了，不把它当事实，只把它当调查入口，顺着它去找第一批代码证据
2. 一边查，一边更新对 issue 说法的判断
3. 如果发现 issue 不成立，就结束
4. 如果发现大方向成立，再审慎决定调查面要不要扩展
5. 整个过程中始终避免两个极端：太早信第一个解释 和 为了全面而无限扩散
6. 最后得出结论：这个问题是否在当前代码库中成立；如果成立，证据和逻辑链是什么，提出假设；如果不成立，问题出在哪里。
