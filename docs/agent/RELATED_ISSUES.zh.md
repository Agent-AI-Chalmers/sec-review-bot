# Agent 相关问题

语言：[English](RELATED_ISSUES.md) | 中文

本文为 [RELATED_ISSUES.md](RELATED_ISSUES.md) 的中文译文；如有差异，以英文版为准。

本文记录本项目在 Agent 能力、上下文、缓存和压缩上的设计判断。

## 上下文上限和压缩机制探讨

长对话或多轮工具调用可能超过模型上下文上限，因此部署 Agent 时需要有处理超限的办法。压缩和裁剪是可选手段，是否提前使用还要评估证据损失和实际成本。

代码 Agent 的压缩配置可参考 [Claude Code 文档](https://support.claude.com/en/articles/14552983-models-usage-and-limits-in-claude-code) 和 [Codex 配置说明](https://developers.openai.com/codex/config-reference)。本项目是否压缩、何时压缩，仍取决于自身运行配置。

提前压缩不一定能降低成本或改善判断，主要需要考虑：

1. 摘要会重新解释原始证据，可能丢失细节。
2. 提示词缓存可能失效。

长上下文如果能命中缓存，不一定比无法命中缓存的短摘要更贵。压缩改变了提示词前缀时，需要按实际缓存命中和未命中价格重新计算。

以下仅沿用原记录中的价格作计算示例，不代表任何服务商的当前报价。假设未命中缓存的单位输入价格是命中缓存的 120 倍，且不计生成摘要的成本，若原文会命中缓存、摘要不会，那么摘要必须小于原文的 `1 / 120`，约 `0.83%`，单次后续请求的输入费用才更低：

```text
120,000 tokens 原文 cache hit:   120,000 * 0.025 / 1,000,000 = 0.003 元
5,000 tokens 摘要 cache miss:      5,000 * 3     / 1,000,000 = 0.015 元
```

因此，不能仅根据压缩后的 token 数判断是否省钱；还需计入摘要生成费用、后续请求次数和缓存变化。压缩也不能丢失继续审查所需的证据。

---

Agent 设计里也有其他的机制用来遏制上下文的恶性增长，如：

1. 工具输出过大：文件系统工具有预算限制。`read` 有文件大小、扫描字节和行窗口限制；`grep` / `glob` / `ls` 有结果数、遍历数和时间限制。Docker `execute` 也会按 `AGENT_DOCKER_MAX_OUTPUT_BYTES` 截断输出。
2. Agent 无限工具循环：可以通过 `AGENT_GRAPH_MAX_STEPS` 或 `AGENT_GRAPH_RECURSION_LIMIT` 限制 LangGraph 执行步数。这个限制约束的是 Agent 和工具调用步骤，不是单次 AI 调用本身的 token 数。

---

原历史记录报告：使用 DeepSeek V4 Pro 的一批运行中，单次模型调用的输入峰值为 210,292 tokens；按该记录使用的 1M tokens 窗口计算，约占 21%。原记录没有提供日期、完整模型版本和运行产物位置，因此这里只保留为历史观察，不能推断其他任务也不会超限，或该模型目前仍提供相同窗口。

这可能是因为本项目不做开放式对话或自由创作。一次 issue / PR / 仓库审查有清晰输入、阶段边界、结构化输出。这可能限制上下文增长，但不保证复杂任务不会超过上限，所以默认压缩机制仍有保底作用。

当前保底机制是 LangChain `SummarizationMiddleware` 加项目定制的 handoff 提示词。一次运行通常从由调用方提供的一份阶段输入开始，所以压缩时必须保留这条输入的边界，并把用户要求和仓库/工具内容分开。

## Agent 是否应该广泛阅读仓库指令和文档？

不应默认要求 Agent 先广泛阅读仓库指令和文档，再开始处理问题。阅读范围应服务于当前任务，而不是把熟悉整个仓库当作前置工作。

更合适的是结合两种做法：

1. **开始时加载仓库指导 `AGENTS.md`。** 提供项目通用要求和必要的文档入口。
2. **从给定任务描述出发。** 围绕 issue、PR 或 case 的目标调查代码，按需补充相关文档。

入口指导提供背景，任务描述决定调查方向。

### 开始时加载仓库指导 AGENTS.md

- **代码无法解释全部契约。** 预期兼容性、部署假设和架构约束可能写在文档里。只沿着问题所指代码调查，可能遗漏这些信息。
- **固定入口可以减少探索。** [AGENTS.md 规范](https://agents.md/) 约定了存放项目指令、构建命令和开发约定的位置。一份简短、持续维护的入口文件，可以避免广泛搜索文档。
- **通用要求不必反复说明。** 把构建命令、测试要求和开发约定集中写进 `AGENTS.md`，并在任务开始时加载，可以减少用户在每个 issue 或 PR 中重复交代的工作。

效果取决于文件内容。加载的指令会在每项任务里占用注意力；过时要求、无关指令，或“通读整个仓库”这样的要求，可能让 Agent 跑偏或花费大量时间探索。自动加载一份入口文件，也不意味着要读完它链接的所有文档。

### 从给定任务描述出发

- **查找和阅读也有成本。** 要求“找到所有相关文档”，容易让 Agent 不断扩大阅读范围。[Anthropic 的上下文工程指南](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 建议只保留最有用的上下文、按需获取资料，也指出探索需要时间，可能找不到有用信息。
- **任务作者需要说清目标。** [GitHub 的 coding-agent 指南](https://docs.github.com/en/copilot/using-github-copilot/coding-agent/best-practices-for-using-copilot-to-work-on-tasks) 要求清晰描述和完整验收条件。[Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices) 要求用户说出代码无法体现的偏好。不能期待 Agent 又快又准地猜出用户没说的要求。
- **让任务决定后续阅读。** 无论是否预加载 `AGENTS.md`，Agent 都可以检查相关代码、调用方、测试和文档。GitHub 也指出，Agent 通常可以在没有精确文件路径时自行定位代码。用户不必提供实现方案。

按需阅读仍可能遗漏文档中的约束。一份简短的入口文件可以帮助提示重要要求，但它和笼统的“多读一些”都不能保证发现全部契约。

## Agent 到底是在审计还是修复？

系统通过显式 `review_intent.objective` 区分 `audit` / `repair`。`review_intent.test_changes` 还可以独立于 objective 约束最终补丁是否允许包含测试改动。因此 Agent 在审计还是修复属于输入契约，模型不需要从任务或自身输出中推断。

`objective` 是调用方设置的执行目标，不保证漏洞存在。GitHub Integration 固定使用 `audit`；本地 Issue CLI 则允许用户选择目标。

## 应该多大程度相信 Agent 的输出？

Agent 输出既不全是事实，也不全是噪声。合理的信任边界取决于输出能否追溯到代码库事实。

模型自报的 `confidence` 或者类似语句不是证据。生产方通常会对自己的判断显得很自信，而消费方真正需要的是可追溯的依据。因此，本项目更看重输出是否能映射回文件位置、调用关系、具体行为、补丁内容、测试结果和产物记录。

能与代码和运行证据对应上的判断可以相对信任。Agent 对自身判断的信心描述不能作为高层决策依据。

## 多阶段 Agent 是否只是把错误分散到多个阶段？

多阶段不能保证不出错，也不能消除错误传播。Analyzer 如果一开始分析错了，Mitigator 可能会沿着错误方向修复；Verifier 有机会挽救，但不能假设一定能挽救。

多阶段的作用是隔离不同任务的偏见。Analyzer 负责形成安全 narrative，Mitigator 负责生成修复，Verifier 负责重新审查补丁覆盖和回归状态。

项目还通过控制提供给 Verifier 的上下文，尽量减少前序结论对它的影响。它接收聚焦所需的分析方向和补丁上下文，但不继承完整的前序 narrative，否则重新验证就没有多少意义。

## 输出结构是在帮助判断，还是在诱导判断？

结构化输出会影响判断。对 Agent 来说，输出格式就是提示词的一部分，因此字段名称、字段层级和字段之间的关系都会影响 Agent 如何组织分析。

输出格式的字段组织方式也代表了作者对问题的认知方式：哪些信息被认为重要，哪些边界被认为需要单独表达，哪些判断需要从证据中拆开。这种认知模型会进入 Agent 的分析过程。Schema 既帮助消费方读取结果，也会引导生产方按这些维度思考；需要避免的是让结构替代证据，或者让字段名制造虚假的确定性。
