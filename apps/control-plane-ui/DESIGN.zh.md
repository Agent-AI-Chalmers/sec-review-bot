# Control Plane UI 设计

语言：[English](DESIGN.md) | 中文

运维人员通过控制台查看系统状态和证据，判断是否需要介入。界面应准确表达状态，让人能读懂证据，并知道操作会带来什么结果。

## 运维信息表达

将运行标识、生命周期状态、失败证据和可用操作放在相邻位置。区分准备、执行和发布：一个阶段成功不代表其他阶段也成功。让运维人员看出系统是否仍在自动恢复、是否已有最终结果，以及是否需要人工决定。

同时使用文字和颜色表达状态。一次尝试失败不一定意味着最终失败；应说明系统能否重试，或是否必须先确认远端结果。解释结果不确定的情况时，不要断言外部写入已经发生或没有发生。

## 语言与状态展示

英文和中文在界面中地位相同。在 [i18n.tsx](browser/shared/i18n.tsx) 中共同维护两种语言的标签和说明。保留代码标识符、run ID 和失败码的原值，通过周围的文字解释，不翻译这些值本身。

运行摘要、筛选器、状态图和事件历史共用状态标签。[status.tsx](browser/features/runs/status.tsx) 负责视觉映射。状态、转换和状态机标题不属于界面文案：它们的中英文都来自生成的状态机模块，由契约和[中文覆盖层](../../contracts/review-runs-api/v1/overlays/zh.yaml)生成，要修改请改那里。[展示测试](test/state-presentation.test.ts) 检查各处在每种语言下显示的标签一致。

## 交互与响应式布局

查询条件改变后，不能让旧结果看起来像新条件的匹配项。刷新相同查询时可以保留可读的结果，但应明确提示数据可能过时以及刷新失败。重试控件放在失败内容附近；可以恢复时，保留用户已输入的有效内容。

窄屏布局应将同一条记录的标识、状态和操作放在一起。可折叠的筛选器必须保留已应用条件的摘要。长标识符和翻译后的标签不能遮挡关键控件。除了触摸和指针操作，还应支持键盘导航和清晰可见的焦点。

在关联记录之间导航时保留调查上下文。操作将改变当前记忆或其他运行状态之前，应说明目标和后果。错误应显示在相关操作内部，让运维人员可以在原处恢复。
