# zap

## Run ZAP

This scan combines a frontend passive pass against the Vite origin with an authenticated OpenAPI-seeded active scan against the backend API. Run it against a disposable local database because active API scanning may create, update, or delete Raddit records.

Start Raddit:

```bash
cd /path/to/raddit
bash ./start.sh
```

Then run ZAP from `evaluation/repo-full-scan-case/raddit/zap`:

```bash
bash -uo pipefail -c '
RADDIT_TOKEN=$(
  curl -sS http://localhost:8080/api/auth/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"admin\",\"password\":\"admin123\"}" \
  | jq -r ".token"
)
if [ -z "$RADDIT_TOKEN" ] || [ "$RADDIT_TOKEN" = "null" ]; then
  echo "failed to fetch admin token" >&2
  exit 1
fi

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py \
  -t http://localhost:5173 \
  -a \
  -j \
  -r zap-frontend-report.html \
  -w zap-frontend-warnings.md \
  -J zap-frontend-report.json || true

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py \
  -t zap-openapi.yaml \
  -f openapi \
  -a \
  -j \
  -r zap-api-report.html \
  -w zap-api-warnings.md \
  -J zap-api-report.json \
  -z "-config replacer.full_list(0).description=auth-header -config replacer.full_list(0).enabled=true -config replacer.full_list(0).matchtype=REQ_HEADER -config replacer.full_list(0).matchstr=Authorization -config replacer.full_list(0).regex=false -config replacer.full_list(0).replacement=Bearer ${RADDIT_TOKEN}" || true
'
```

Clean the combined ZAP output into the reviewed benchmark input:

```bash
./clean-zap-combined-report.sh \
  zap-frontend-report.json \
  zap-api-report.json \
  zap-combined-clean.json
```

This run uses [zap-openapi.yaml](zap-openapi.yaml) to seed backend routes. It is still not equivalent to source review: weak JWT secrets, plaintext password logging, hardcoded credentials, rate limiting, CSRF, and IDOR generally need custom scripts, multi-user scenarios, or source/config/log inspection.

### Clean Report Rules

Manual review treats the response-header and cookie findings as true-positive hardening findings outside the answer key. They are not answer-key coverage because the Raddit answer key focuses on concrete exploit surfaces such as injection, authorization, JWT flaws, CSRF, and unsafe rendering.

The clean report is generated by [clean-zap-combined-report.sh](clean-zap-combined-report.sh). It retains answer-key findings, reviewed extra hardening surfaces, weak non-covering 5xx signals, and reviewed false positives. It excludes frontend runtime paths such as `/@vite/client`, `/@react-refresh`, `/src/...`, and `/node_modules/.vite/...`; informational alerts such as `Base64 Disclosure`, `Suspicious Comments`, `Modern Web Application`, `Sec-Fetch-* Header is Missing`, and `Storable ... Content`; and the `Information Disclosure - Sensitive Information in URL` probe on `/?token=...`.

For the API report, the clean script excludes `A Client Error response code was returned by the server` because it mostly records expected 400/401/404 responses from route probing. `Authentication Request Identified`, `Non-Storable Content`, and API `Sec-Fetch-*` informational alerts are also excluded from benchmark scoring.

Two alert groups are retained as weak, non-covering signals. The frontend `Application Error Disclosure` alert and the API `A Server Error response code was returned by the server` alert both show 5xx behavior, but they do not show stack traces, sensitive error bodies, SQL error text, or exploit-specific evidence. They are therefore not counted as answer-key coverage.

The `Format String Error` alert on `POST /api/auth/register` is classified as a reviewed false positive. The evidence is connection closure during a `%n%s...` password probe, and the Go/Gin registration path does not evaluate user input as a format string.

## Summary

The reviewed clean ZAP report contains 16 application-relevant alert groups from the combined frontend passive scan and backend OpenAPI active scan. Manual mapping to the 22-item Raddit answer key shows 3 covered answer-key vulnerabilities and 19 not covered; answer-key recall is 3 / 22 = 13.6%. The clean report also preserves raw input counts for auditability.

The OpenAPI-seeded API scan produced strong evidence for password-hash exposure and command injection, plus a low-confidence SQL injection alert for the search endpoint. It did not cover most authenticated workflow, token-design, source/configuration, CSRF, IDOR, upload-validation, or stored-rendering issues.

## Interpretation

The OpenAPI-seeded backend scan reaches backend routes and produces real findings for search SQL injection, command injection, and password-hash exposure. However, ZAP misses most answer-key items because they require either source/config/log inspection, multi-user authenticated workflows, stateful object ownership tests, JWT-specific custom payloads, or stored frontend rendering checks.

For this benchmark, ZAP should be interpreted as a useful DAST supplement rather than a repository full-scan replacement. It adds coverage for externally reachable sink behavior, but it does not reason about code-level defaults, logging, authorization policy, CSRF architecture, or multi-step repair boundaries.
