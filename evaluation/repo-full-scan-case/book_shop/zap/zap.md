# zap

## Run ZAP

This scan combines a frontend passive pass against the Next.js origin with an authenticated OpenAPI-seeded active scan against the same origin. Run it against a disposable local database because the active API scan can create, update, delete, and export Book Shop records.

Set `.env`:

```env
DATABASE_URL="file:./dev.db"
```

```bash
npm install
npm run dev
```

Then run ZAP from `evaluation/repo-full-scan-case/book_shop/zap`:

```bash
bash -uo pipefail -c '
BOOK_SHOP_BASE="http://localhost:3001"

# Book Shop does not seed a default user. Create one for scanning, then log in.
curl -sS "${BOOK_SHOP_BASE}/api/auth/register" \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"zap\",\"email\":\"zapadmin@example.test\",\"password\":\"zapPassword123!\"}" \
  >/dev/null || true

BOOK_SHOP_LOGIN_RESP="$(
  curl -sS "${BOOK_SHOP_BASE}/api/auth/login" \
    -H "Content-Type: application/json" \
    -d "{\"email\":\"zapadmin@example.test\",\"password\":\"zapPassword123!\"}"
)"
BOOK_SHOP_TOKEN="$(printf "%s" "$BOOK_SHOP_LOGIN_RESP" | jq -r ".token")"
if [ -z "$BOOK_SHOP_TOKEN" ] || [ "$BOOK_SHOP_TOKEN" = "null" ]; then
  echo "failed to fetch admin token" >&2
  echo "login response: $BOOK_SHOP_LOGIN_RESP" >&2
  exit 1
fi

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py \
  -t http://localhost:3001 \
  -a \
  -j \
  -r zap-frontend-report.html \
  -w zap-frontend-warnings.md \
  -J zap-frontend-report.json || true

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py \
  -t zap-openapi.yaml \
  -f openapi \
  -a \
  -j \
  -r zap-api-report.html \
  -w zap-api-warnings.md \
  -J zap-api-report.json \
  -z "-config replacer.full_list(0).description=auth-header -config replacer.full_list(0).enabled=true -config replacer.full_list(0).matchtype=REQ_HEADER -config replacer.full_list(0).matchstr=Authorization -config replacer.full_list(0).regex=false -config replacer.full_list(0).replacement=Bearer ${BOOK_SHOP_TOKEN}" || true
'
```

Clean the combined ZAP output into the reviewed benchmark input:

```bash
./clean-zap-combined-report.sh \
  zap-frontend-report.json \
  zap-api-report.json \
  zap-combined-clean.json
```

This run uses [zap-openapi.yaml](zap-openapi.yaml) to seed backend routes. It is still not equivalent to source review: SQL injection, JWT design flaws, CSRF, IDOR, path traversal, command injection, insecure deserialization, SSRF, and open redirect generally need custom scripts or direct source/config inspection.

### Clean Report Rules

Manual review treats the response-header and cookie findings as true-positive hardening findings outside the answer key. They are not answer-key coverage because the Book Shop answer key focuses on concrete exploit surfaces such as injection, authorization, session/JWT flaws, CSRF, unsafe rendering, unsafe file/path boundaries, and dangerous admin operations.

The clean report is generated by [clean-zap-combined-report.sh](clean-zap-combined-report.sh). It retains answer-key findings, reviewed extra hardening surfaces, reviewed 5xx signals, and reviewed informational probes needed for context. It excludes common Next.js runtime noise such as `/_next/static/`, `/_next/webpack-hmr`, scanner fingerprint paths, and `no-actionable-finding` dev-server artifacts.

For this benchmark, the `A Server Error response code was returned by the server` group is retained as a weak signal but not counted as answer-key coverage unless it contains exploit-specific evidence (for example, SQL error text, stack traces with sensitive internals, or successful exfiltration). In this clean report, the evidence is limited to `HTTP/1.1 500 Internal Server Error` and is therefore not treated as coverage on its own.

The `Information Disclosure - Sensitive Information in URL` alert is kept as context only. It shows a sensitive identifier in a request URL, but it does not prove broken access control or IDOR without a cross-user access demonstration.

## Summary

The reviewed clean ZAP report contains 17 application-relevant alert groups from the combined frontend passive scan and backend OpenAPI active scan (generated on 2026-05-09). Manual mapping to the 19-item Book Shop answer key shows 1 covered answer-key vulnerability and 18 not covered; answer-key recall is 1 / 19 = 5.3%. The clean report also preserves raw input counts for auditability.

ZAP produced one high-risk finding (SQL injection) with low-confidence evidence based on `500 Internal Server Error` responses. It also produced multiple response-header/cookie hardening findings. It did not cover most answer-key items because they require either source/config/log inspection, multi-step authenticated workflows, stateful ownership tests, JWT-specific payloads, CSRF validation, or frontend rendering checks that ZAP does not prove by default.

## Interpretation

The OpenAPI-seeded backend scan reaches API routes and produces at least one injection signal for the search endpoint. However, ZAP misses most answer-key items because they require source-level reasoning, multi-user authorization workflows, CSRF architecture validation, JWT-specific crafted tokens, or exploit verification steps that are not covered by default scanning.

For this benchmark, ZAP should be interpreted as a useful DAST supplement rather than a repository full-scan replacement. It adds coverage for externally reachable sink behavior, but it does not reason about code-level defaults, logging, authorization policy, CSRF protections, or multi-step repair boundaries.
