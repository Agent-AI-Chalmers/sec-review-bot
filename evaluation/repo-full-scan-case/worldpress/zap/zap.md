# zap

## Run ZAP

This scan combines a frontend passive pass against the Vite origin with an authenticated OpenAPI-seeded active scan against the Flask backend API. Run it against a disposable local database because the active API scan can create, update, delete, and export WorldPress records.

Start WorldPress:

```bash
cd /path/to/worldpress
bash ./start.sh
```

Then run ZAP from `evaluation/repo-full-scan-case/worldpress/zap`:

```bash
bash -uo pipefail -c '
WORLDPRESS_TOKEN=$(
  curl -sS http://localhost:5000/api/auth/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"admin\",\"password\":\"admin123\"}" \
  | jq -r ".token"
)
if [ -z "$WORLDPRESS_TOKEN" ] || [ "$WORLDPRESS_TOKEN" = "null" ]; then
  echo "failed to fetch admin token" >&2
  exit 1
fi

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py \
  -t http://localhost:3001 \
  -a \
  -j \
  -r zap-frontend-report.html \
  -w zap-frontend-warnings.md \
  -J zap-frontend-report.json || true

docker run --rm -t \
  --network host \
  -v "$(pwd):/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py \
  -t zap-openapi.yaml \
  -f openapi \
  -a \
  -j \
  -r zap-api-report.html \
  -w zap-api-warnings.md \
  -J zap-api-report.json \
  -z "-config replacer.full_list(0).description=auth-header -config replacer.full_list(0).enabled=true -config replacer.full_list(0).matchtype=REQ_HEADER -config replacer.full_list(0).matchstr=Authorization -config replacer.full_list(0).regex=false -config replacer.full_list(0).replacement=Bearer ${WORLDPRESS_TOKEN}" || true
'
```

Clean the combined ZAP output into the reviewed benchmark input:

```bash
./clean-zap-combined-report.sh \
  zap-frontend-report.json \
  zap-api-report.json \
  zap-combined-clean.json
```

This run uses [zap-openapi.yaml](zap-openapi.yaml) to seed backend routes. It is still not equivalent to source review: weak JWT secrets, hardcoded credentials, plaintext password logging, rate limiting, CSRF, IDOR, XXE, SSRF, command injection, and insecure deserialization generally need custom scripts or direct source/config/log inspection.

### Clean Report Rules

The combined clean script is generated by [clean-zap-combined-report.sh](clean-zap-combined-report.sh). It retains answer-key findings, reviewed extra hardening surfaces, and weak non-covering 5xx signals. It excludes frontend runtime paths such as `/@vite/client`, `/@react-refresh`, `/@id/`, `/@fs/`, `/__vite`, `/node_modules/`, and `/src/`; informational alerts such as `Base64 Disclosure`, `Suspicious Comments`, `Modern Web Application`, `Sec-Fetch-* Header is Missing`, and `Storable ... Content`; and scanner-noise probes such as `A Client Error response code was returned by the server`, `Authentication Request Identified`, and `Information Disclosure - Sensitive Information in URL`.

For the API report, the clean script excludes `A Client Error response code was returned by the server` because it mostly records expected 400/401/403/404 responses from route probing. `Authentication Request Identified`, `Non-Storable Content`, and API `Sec-Fetch-*` informational alerts are also excluded from benchmark scoring.

One alert group is retained as a weak, non-covering signal: the API `A Server Error response code was returned by the server` alert. It shows 5xx behavior, but it does not show stack traces, sensitive error bodies, SQL error text, or exploit-specific evidence. It is therefore not counted as answer-key coverage or reviewed precision.

No reviewed false-positive alert group is present in the evaluated clean report.

## Summary

The reviewed clean ZAP report contains 12 application-relevant alert groups. Manual mapping to the 21-item WorldPress answer key shows 2 covered answer-key vulnerabilities and 19 not covered; answer-key recall is 2 / 21 = 9.5%. The clean report also preserves raw input counts for auditability.

For reviewed precision, the two answer-key SQL injection surfaces and eight extra hardening surfaces are counted as true positives. The retained weak 5xx group is excluded from the precision denominator because it is useful triage context but does not establish a concrete vulnerability. No reviewed false-positive alert group is present.

The OpenAPI-seeded API scan produced strong evidence for login SQL injection and post-search SQL injection, plus a low-confidence SQL injection alert for the category and status filters. It did not cover most authenticated workflow, token-design, source/configuration, CSRF, IDOR, upload-validation, path traversal, SSRF, command injection, or stored-rendering issues.

## Interpretation

The OpenAPI-seeded backend scan reaches backend routes and produces real findings for login and search SQL injection. However, ZAP misses most answer-key items because they require source/config/log inspection, multi-user authenticated workflows, stateful object ownership tests, JWT-specific custom payloads, or stored frontend rendering checks.

For this benchmark, ZAP should be interpreted as a useful DAST supplement rather than a repository full-scan replacement. It adds coverage for externally reachable sink behavior, but it does not reason about code-level defaults, logging, authorization policy, CSRF architecture, or multi-step repair boundaries.
